# M1 — Revalidate the ChatGPT Loop

## Goal

Verify and repair the existing extension against the current ChatGPT web UI before building new server complexity.

## Implementation note — 2026-08-22

The restart branch now contains the first revalidation hardening pass: composer/send selectors are scoped and ranked more conservatively, the overlay can export DOM/selector diagnostics, and tool calls keep an in-memory correlated state trace. These changes are implemented but runtime-sensitive boxes remain unchecked until verified in a real current ChatGPT session.

The first Windows acceptance run verified a clean `npm ci`, all current tests, and a successful patched `npm run build` for both extension and broker. The unpacked extension was then loaded in current Edge and the **Tool Shim · restart** overlay rendered successfully on `chatgpt.com`.

The first live conversation traffic verified that the current assistant-message selector detects real model output and that `hello`, `clock`, and `browser.tabs.list` execute end-to-end. With Auto Submit disabled, each result was inserted into the ChatGPT composer and could be manually submitted, verifying insert-only delivery. The large `browser.tabs.list` response also demonstrated that ordinary inline delivery remains functional for the current result size.

A later `hello` call was initially misclassified as a successful Auto Submit test because the result appeared in the conversation; the user clarified that they had manually pressed Send. The first verified retry then exposed a concrete failure: the shim found an enabled control and invoked `.click()`, but ChatGPT did not consume the composer within five seconds. The success result and compact `RESULT_DELIVERY_ERROR` remained together in the composer and were later manually submitted, proving the programmatic click had not produced a send transaction.

A subsequent observation showed that the shim also opened ChatGPT's **plus/add files/apps/modes** menu during an Auto Submit attempt. Inspection found the submit selector still accepted generic `button[type="submit"]` controls and rewarded `type="submit"` during fallback ranking. That is no longer allowed: candidate controls must now carry positive Send semantics (`send-button`, `Send prompt`, `Send message`, or equivalent), while add/files/apps/tools/modes/menu/plus/attachment controls are explicitly rejected. If no positively identified Send control exists, the shim fails safely rather than clicking another composer control.

The submit implementation uses a verified fallback ladder rather than trusting `.click()`: first the composer form's native `requestSubmit()`, then synthetic mouse activation on the selected send control, then an Enter-key fallback. Each attempt is accepted only after a real page-side success signal is observed (composer cleared or a new `[data-message-author-role="user"]` node appears). If all methods fail, the error records the selected button's type/test-id/aria-label/form association plus the outcome of every attempted activation method.

The next strict-selector live `hello` test succeeded completely hands-free: the extension detected the assistant tool call, executed `hello`, inserted the result, selected the real Send control, and submitted the result back into the conversation with **no user click on Send**. The user explicitly confirmed that the result submitted itself. Auto Submit is therefore verified in the current normal composer state. Streaming-state send behavior remains intentionally unchecked.

That same testing exposed that identical autogenerated calls reused a content-derived call ID across page reloads (`call_52f675cf`). The parser was subsequently changed so autogenerated IDs combine a random per-content-script session nonce with a stable content hash: rescans in one page lifetime keep the same ID/fingerprint for dedupe, while the same call after a reload gets a distinct execution ID. Later live calls returned session-qualified IDs such as `call_f05c7fd81b136353_52f675cf`, verifying the session-unique execution-ID behavior. Explicit model-provided IDs remain preserved.

The restart HUD is draggable by its title bar, persists its viewport-constrained position, and now has a persistent minimize/expand control so it can collapse to a small header while reading. Permission-gated requests remain visible/actionable while minimized.

Background-tab hardening is implemented for the core page loop. Tool-call scanning no longer waits on a 500 ms page timer after `MutationObserver` fires; it uses a microtask-driven serialized scan queue instead. Composer/send and attachment waits keep timer deadlines as failure backstops but also wake immediately on relevant DOM mutation, reducing dependence on Chromium's hidden-tab timer budget. Every trace event records `document.visibilityState` and `document.hasFocus()`.

The first live **hidden-tab** acceptance test failed in an informative way. The user switched away from the ChatGPT tab and later returned to find the pending result submit immediately. Diagnostics showed that the entire call lifecycle — `DETECTED`, `VALIDATED`, `DISPATCHED`, result receipt/packaging, `SUBMITTING`, and `SUBMITTED` — began only after the page had returned to `visibility=visible; focused=true`. No hidden/unfocused trace event was emitted. This means timer throttling was not the remaining blocker: the current DOM-driven adapter did not receive/observe the assistant DOM update while the ChatGPT tab was hidden. Edge's "never sleep" exemption alone is therefore insufficient for a hidden background tab in this architecture.

The first **visible-but-window-unfocused** test also failed without an extension-level wakeup: ChatGPT stayed selected in its own non-minimized Edge window, but the lifecycle began only after Edge regained focus.

A service-worker experiment then changed the result. The HUD's **Arm BG Probe 30s** repeatedly called `chrome.scripting.executeScript({ target: { tabId } })` against the originating ChatGPT tab. During the acceptance run, the probe successfully inspected the tab while `document.hasFocus()` was false and observed the newly rendered assistant `<tool_call>` before focus returned. More importantly, the ordinary content-script loop itself then completed `DETECTED`, `VALIDATED`, `DISPATCHED`, result packaging, `SUBMITTING`, and `SUBMITTED` while `visibility=visible; focused=false`.

That experiment has now been promoted into a persistent **Background Mode** scoped to the ChatGPT tab where it is enabled. The service worker periodically targets that tab by ID so the ordinary loop continues progressing while the user works elsewhere. A subsequent live `hello` acceptance run was explicitly confirmed by the user to have auto-submitted while Edge remained unfocused, with no manual interaction. Persistent visible-window background execution is therefore verified. Hidden-tab behavior remains a separate unresolved case and must not be inferred from the unfocused-window success.

The first large-result acceptance run under persistent Background Mode partially succeeded. A 1.25 MiB broker result was generated, attached, and surfaced as a model-readable result artifact, but the final attachment-bearing Auto Submit failed. The shim selected the correct enabled Send control and invoked all three activation methods; none produced the existing composer-cleared/user-message-added acknowledgement within the configured 1,750 ms observation window. This failure is now characterized separately from safe inline background execution: background execution itself works, while attachment-bearing submission needs a stronger readiness/acknowledgement strategy.

The canonical local iteration command is now the full extension+broker refresh sequence:

```powershell
git pull --ff-only; npm test; npm run build; npm run server:start
```

This keeps browser and broker artifacts synchronized during the restart instead of optimizing for partial rebuilds.
